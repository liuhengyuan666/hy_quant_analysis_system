# 功能模块与处理逻辑

本文档按模块梳理当前系统的职责边界、数据来源、输入输出与主要处理逻辑。

---

## 1. 模块分层

当前系统可分成 4 层：

1. **配置与数据源层**
2. **分析引擎层**
3. **编排与存储层**
4. **应用与展示层**

## 2.2 `crates/data-ingestion`

### 作用

负责所有外部数据抓取。

### 数据来源

- Eastmoney
- Tencent
- FRED

### 核心逻辑

- `load_universe()`：加载标的池
- `fetch_eastmoney_daily_bars()`：主源拉取日线
- `fetch_tencent_daily_bars()`：fallback 日线
- `fetch_daily_bars()`：统一抓数入口
- `fetch_fred_series()` / `fetch_fred_series_with_status()`：拉宏观因子
- `normalize_daily_bar()`：统一日线校验

### 输出

- `DailyBar`
- `MacroFactorSeries`

### 当前规则

 - 日线统一为前复权口径
 - provider fallback 在这里完成
 - 宏观支持 FRED API 主路径（`api.stlouisfed.org/fred`），支持配置开关（`config/fred.toml`）
 - FRED 获取可配置：启用时通过 API 获取，禁用时使用 ClickHouse 已存数据
 - FRED 限流：500ms 请求间隔，API Key 通过 `config/fred.toml` 配置（支持环境变量插值）

## 3.6 `crates/execution-engine`（V5 新增）

### 作用

Execution Layer — 收盘前执行过滤器（Pattern Library）。

### 定位

- 不产生投资想法，只决定执行时机
- 只回答 "When"，不回答 "What"
- 物理隔离为独立 crate，单向消费现有信号

### 输入

- `StrategyState`（hard gate: state ≠ NO_TRADE）
- `SignalSnapshot`（候选 gate: signal ≥ Buy）
- `IntradaySnapshot`（实时数据：Tencent API）
- `IndicatorSnapshot`（MA10 / vol_ma20 用于 enrichment）

### 输出

- `ExecutionDecision`（BuyNow / Wait / NoChase / Reduce / Skip）
- `reports/execution-samples/YYYY-MM-DD.json`

### 三个 Pattern

| Pattern | 条件 | 输出 |
|---------|------|------|
| NoChase | `today_return>2% && distance_ma10>4% && volume_ratio>1.8` | `NoChase` |
| Distribution | `today_return<-1.5% && volume_ratio>1.5 && close_position<0.2` | `Reduce` |
| StrongClose | `today_return>1% && close_position>0.8 && volume_ratio>1.3` | `BuyNow` |

### 当前特点

- 纯内存，无 ClickHouse/SQLite 新表
- 失败降级：Tencent API 失败 → 全部 `Skip`
- 90 天内仅作为观测工具（ADR-071）

## 9. `research-skills`（V4.5 重构后）

### 作用

Research Layer — 冻结量化引擎之上的只读叙事层。没有 Skill Framework，没有 Agent Registry，没有 Router。只有 5 个 prompt 常量 + 一个 `build_prompt` 函数。

### 核心结构

```
crates/research-skills/
├── src/
│   ├── lib.rs              # 模块声明 + re-exports
│   ├── action.rs           # 5 个 const PROMPT + build_prompt() + build_snapshot_context()
│   ├── provider.rs         # LlmProvider trait
│   ├── openai_provider.rs  # OpenAI-compatible API implementation
│   └── inference.rs        # 推理配置
```

### 5 个研究动作

| Action | 中文名 | 角色 | 任务 |
|--------|--------|------|------|
| `market_story` | 市场叙事 | 资深研究员 | 今天市场发生了什么 |
| `explain_decision` | 解释决策 | 系统分析师 | 为什么系统做出这样的决策 |
| `preclose_review` | 收盘前复核 | 执行分析师 | 为什么 Execution 给出这样的建议 |
| `risk_view` | 风险视角 | 风控总监 | 我最担心什么 |
| `devils_advocate` | 唱反调 | 质疑者 | 系统可能错在哪里 |

### 治理约束（ADR-074）

- **只读**：解释、质疑、提供上下文、讲述历史。禁止创建信号、评分、排序、覆盖决策。
- **输出 Markdown 纯文本**：禁止 JSON schema、confidence、score、ranking、probability。
- **不传评分数据给 LLM**：`build_snapshot_context` 只给 symbol + label + rank order，不给 score/RS/CAGR/Sharpe/MaxDD。
- **90 天冻结**：90 天内禁止新增 Pattern、前端面板、定时调度、Backtest v2、参数优化、性能声称。

### 当前特点

- 没有 enum。没有 registry。没有 router。只有 `build_prompt(action, snapshot)` 函数。
- 系统 prompt 按 action 分化（研究员 / 风控总监 / 质疑者），但没有 "agent 选择" UI。
- 支持 OpenAI-compatible API 和 PlaceholderProvider 降级。
- 旧 V4 Skill Framework 文件（skill.rs, registry.rs, agent_profile.rs, router.rs, reasoning.rs, executor.rs, schema.rs）已删除或标记为死代码。

## 10. V8 Research Asset 模块

### 10.1 `crates/app-service/src/research_evidence.rs`

#### 作用

负责把 V6/V7 的研究条件转换成真实、可复现的 `Evidence` 结构。

#### 输入

- `scope`：分析范围（`GLOBAL / CN / HK`）
- `condition`：条件标签（如 `srd-strong`、`stretch-extreme-crowding-momentum`）
- `horizon`：前向收益窗口（交易日数，如 20 / 60）
- `date_range`：可选历史日期范围
- `AppContext`：用于访问 ClickHouse 中的 `signal_snapshot`、`rotation_rank`、`market_regime`、`daily_bar`

#### 处理逻辑

1. 从 ClickHouse 读取条件发生日及其前后窗口的数据
2. 按条件标签匹配每一天是否满足条件
3. 对满足条件的日子，计算未来 N 个交易日的收益率
4. 汇总统计量：
   - `occurrences`：条件发生次数
   - `forward_return_median` / `mean` / `best` / `worst`
   - `positive_ratio`
   - `max_drawdowns`：每次持有期内的最大回撤序列
   - `median_max_drawdown`
5. 生成 `Evidence` 结构体，包含 `dataset_hash` 与 `config_hash`

#### 输出

- `Evidence`（`core-domain::research::attribution::Evidence`）
- 可选：通过 `WorkspaceManager` 写入 `workspace/evidence/`

### 10.2 `crates/app-service/src/workspace.rs`

#### 作用

V8 Research Asset 的持久化与索引中枢。负责统一身份、统一生命周期、目录管理、索引维护。

#### 输入

- `Evidence`：由 `research_evidence` 产出
- `Snapshot`：由 V7 orchestration 构建
- `AssetKind`：区分 Evidence / Snapshot / 未来扩展类型
- 用户配置：workspace 根目录（默认 `workspace/`）

#### 处理逻辑

1. **统一身份生成**
   - 新 Asset 分配 `RA-XXXXXX`（6 位大写数字字母）
   - 现有 `EV-` / `SN-` 前缀的资产被 grandfathered，但新写入不再使用

2. **统一生命周期**
   - `Draft`：由计算/重放直接产出
   - `Verified`：通过自动审计（hash 一致、依赖存在、scope/date 有效）
   - `Published`：进入稳定引用
   - `Superseded`：被新版本替代
   - `Archived`：过期保留

3. **目录写入**
   - Evidence：`workspace/evidence/{subpath}/RA-XXXXXX.json`
   - Snapshot：`workspace/snapshots/RA-XXXXXX.json`

4. **索引维护**
   - `workspace/registry/evidence-index.json`
   - `workspace/registry/snapshot-index.json`
   - 索引记录：id、kind、version、scope、created_at、state、dataset_hash、config_hash

5. **引用解析**
   - Snapshot 通过 `EvidenceRef { id, version }` 引用 Evidence
   - 写入时校验被引用的 Evidence 在索引中存在

#### 输出

- 持久化的 JSON Asset 文件
- 更新的 registry 索引文件
- 返回 `ResearchAssetId` 给调用方

### 10.3 CLI 侧 V8 集成

#### `apps/cli/src/main.rs`

- 新增 `--save-evidence` 全局 / 子命令参数
- 透传给 `research analytics` 的 orchestration 入口

#### `apps/cli/src/commands/research.rs`

- `research analytics` 在不带 `--save-evidence` 时，只输出终端结果
- 带 `--save-evidence` 时，调用 `app-service::research_evidence` 计算 Evidence，再调用 `WorkspaceManager` 写入 workspace

### 10.4 使用原则

- V8 只改变研究产物的持久化方式，不改变 V6/V7 的计算语义。
- `--save-evidence` 是显式 opt-in；默认行为仍是临时输出。
- P3 之前不引入 Evidence 权重；当前只负责统一格式、统一身份、统一生命周期和持续积累。
