# 阶段性更新（2026-04-26）

本文档用于总结当前这一轮已经落地的阶段性成果，帮助你快速了解：

- 哪些问题已经处理完
- 当前系统与几天前相比有什么关键变化
- 接下来最自然的推进方向是什么

---

## 1. 这轮工作的总目标

这一轮不是继续“堆功能”，而是先把当前系统里最容易误导用户、最容易让后续实现继续漂移的部分收紧。

核心关注点有三条：

1. **规则与记忆落地**
2. **桌面端前端结构减压**
3. **用户语义与研究流程收敛**

这意味着：

- `main.js` 现在更聚焦于：
  - 全局 state

## 2.6 刷新链路已经具备最小可用的阶段控制

这轮我们没有把 refresh 做成完整 workflow engine，但已经补上最关键的恢复能力。

当前已支持：

- 默认 `Refresh data`
- `Retry failed stage`
- `Run from stage`

支持的阶段：

- `ingest`
- `indicators`
- `macro`
- `rotation`
- `strategy`
- `signals`
- `backtests`

并且采用的是：

> **suffix-run 模式**

也就是：

- 从指定阶段开始
- 一直跑到最终一致性校验结束
- 不支持 stop-at-stage / cancel / resume / persisted job state

---

## 2.7 针对 signal 落后导致默认导出日期被卡住的问题，已补上提示和机制性防呆

已完成：

- `PipelineDateDiagnostics.alerts`
- 当 `strategy_preference` 新于 `signal_snapshot` 时，明确提示先重跑 `compute-signals`
- 当 `signal_snapshot` 最新日 coverage 不完整时，也会发出同类告警
- `compute-signals` 和 desktop refresh 都加入了 fail-loud 机制
- refresh 最终一致性校验现在覆盖 `GLOBAL / CN / HK`

这意味着：

- 系统不再容易出现“看起来跑成功了，但 dashboard/export 默认日期仍然落后”的假成功态

## 4. 当前还没完成，但已经明确方向的后续项

### 4.1 `Recent reports` 下一阶段

最自然的继续方向是：

- `compare previous`

这是把 recent reports 从“轻量入口”推进到“真正研究结果管理”的下一步。

### 4.2 refresh 更重的控制能力

当前还没有：

- cancel
- resume
- persisted job state
- job history

这些都属于更重的一层，不是这轮的目标。

### 4.3 更深层的 transactional / staging 改造

当前 signal / strategy 的 fail-loud 与 end-state validation 已经足够把最危险的假成功挡住，
但如果以后要再往下做，会是：

- staging table
- run_id
- promote/commit 模型
