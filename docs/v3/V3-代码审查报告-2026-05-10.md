## 严重问题（CRITICAL）

### 1. `apps/cli/src/main.rs` 缺少 `use anyhow::Context` 导入 — 编译失败

**位置**：`apps/cli/src/main.rs:1` + `347-351`

```rust
use anyhow::Result;  // 只导入了 Result，没有导入 Context trait
// ...
let latest = dates.first().context(
    "no dashboard dates available; run refresh-all first",
)?;
```

**问题**：`dates.first()` 返回 `Option<&String>`，调用 `.context()` 需要 `anyhow::Context` trait。当前文件只 `use anyhow::Result;`，没有 `use anyhow::Context;`，这将导致 **编译错误**。

**影响**：`cargo check -p quant-cli` 会直接失败。提交信息中提到"Network blocker: cargo check --workspace pending... All code written and verified via rustfmt/LSP"，说明这段代码实际上从未经过编译验证。

**建议**：在 `apps/cli/src/main.rs` 第一行改为 `use anyhow::{Context, Result};`。

---

### 2. `analyze_report_with_llm` 在同步函数内新建 tokio Runtime — 可能 panic

**位置**：`crates/app-service/src/lib.rs:3289`

```rust
let runtime = tokio::runtime::Runtime::new().context("failed to create tokio runtime")?;
let analysis_text = runtime.block_on(async { ... });
```

**问题**：在同步函数内部新建 `tokio::runtime::Runtime` 是 Rust 异步编程中的典型反模式。如果该方法被任何已运行在 tokio runtime 内的调用方调用（例如未来某个 async Tauri command 直接调用它），会触发 **panic**：
> "Cannot start a runtime from within a runtime"

**影响**：当前 CLI 调用路径是同步的，因此不会触发；但一旦桌面端或任何 async 上下文直接调用此方法，程序会崩溃。

**建议**：
- 将 `analyze_report_with_llm` 改为 `async fn`，由调用方选择 runtime；或
- 使用 `tokio::task::block_in_place` + `Handle::current()` 来检测并复用现有 runtime；或
- 至少在该方法文档和命名上明确标注 "must be called from non-async context"。

### 3. `LlmConfig.timeout_secs` 被存储但从未实际使用

**位置**：`crates/core-domain/src/lib.rs`（类型定义）、`crates/app-service/src/lib.rs:3291-3317`（调用端）

**问题**：`LlmConfig` 包含 `timeout_secs: u64`，`set_llm_config` 和 `get_llm_config` 完整读写该字段，但 `analyze_report_with_llm` 创建 `async_openai::Client` 时完全没有应用该超时。LLM API 调用将无限期阻塞，直到 OS TCP 层超时或服务器断开。

**影响**：网络抖动或服务端异常时，调用方会挂死而非收到可控超时错误。

**建议**：在 `async_openai::Client` 或请求层配置 `reqwest` timeout（`async_openai` 底层为 `reqwest`），或通过 `reqwest::ClientBuilder.timeout()` 注入自定义 HTTP client。

## 高风险问题（HIGH）

### 4. `set_llm_api_key` 在 keyring 成功时把 SQLite fallback 清空，导致后续 keyring 不可用时密钥丢失

**位置**：`crates/app-service/src/lib.rs:3240-3251`

```rust
Ok(()) => {
    let _ = market_store::insert_credential(&self.storage, "llm_api_key", "");
    Ok(())
}
```

**问题**：
1. keyring 写入成功时，SQLite 被写入空字符串（意图是"清除旧 fallback"）。
2. `get_llm_api_key` 在 keyring 返回 `NoEntry` 或空字符串时，会回退到 SQLite。
3. 触发场景：用户先在有 keyring 的环境设置 API key → SQLite 被清空 → 之后在同一台机器切换到无 keyring 环境（如某些 CI、容器、或 keyring daemon 崩溃）→ `get_llm_api_key` 回退到 SQLite → 拿到空字符串 → 密钥永久丢失。

**建议**：要么在 keyring 成功时**同时**把同一密钥写入 SQLite 作为冗余备份（而非空字符串），要么在 `get_llm_api_key` 的 fallback 路径中明确区分"SQLite 无记录"和"SQLite 记录为空字符串"，后者应视为未配置而非有效 fallback。

---

### 4. API key 以明文形式存储在 SQLite `credential_store`

**位置**：`crates/market-store/src/lib.rs`（`credential_store` 表结构及读写方法）

**问题**：`credential_store` 表的 `credential_value` 字段为纯 `TEXT`，没有任何加密。虽然 keyring 是首选存储，但 fallback 路径意味着 API key 会以明文落盘。如果用户机器被入侵或数据库文件被意外分享，密钥直接暴露。

**影响**：安全合规风险；与 LLM provider 的 API key 泄露可能导致费用盗刷或数据泄露。

**建议**：
- 短期：在 CLI `set-llm-api-key` 帮助文本和 keyring fallback warning 中明确提示"密钥将以明文形式存储在本地 SQLite 中"。
- 中期：对 SQLite fallback 的 credential 做至少 base64 或简单对称加密（如用机器 fingerprint 作为密钥），使直接读取数据库文件不会立即暴露明文 key。

---

### 5. 桌面端 `refresh_pipeline` 调用传入 `None` progress callback，导致进度反馈丢失

**位置**：`apps/desktop/src-tauri/src/lib.rs:405-412`

```rust
let result = context.refresh_pipeline(
    today,
    app_service::ReportScope::Global,
    true,
    Some(worker.cancel_flag.as_ref()),
    start_stage.map(RefreshStartStage::as_str),
    None,  // <-- progress_callback 为 None
);
```

**问题**：v3 将进度回调统一集中到 `app-service`，但桌面端调用时传入了 `None`。此前桌面端通过 `RefreshStartStage::progress_after()` 自行维护阶段进度元数据；v3 将该元数据下沉到 `pipeline_stages` 模块后，桌面端没有相应地把进度回调桥接回来。

**影响**：桌面端刷新期间，前端可能失去或无法获得各阶段开始/结束的进度事件（取决于前端是否完全依赖 Tauri 命令轮询 `DashboardRefreshStatus`）。如果前端曾依赖阶段进度消息更新 UI，这是一次行为退化。

**建议**：在桌面端 `spawn_dashboard_refresh` 中构造一个进度回调，通过 `worker` 状态或 Tauri event 将进度消息转发到前端，恢复 v3 之前的进度可见性。

## 中风险问题（MODERATE）

### 6. `ingest_daily` 阶段没有接入 progress callback，造成进度报告不一致

**位置**：`crates/app-service/src/lib.rs:1521-1530`

```rust
let cb: Option<&dyn Fn(&str)> = progress_callback
    .as_ref()
    .map(|b| b.as_ref() as &dyn Fn(&str));

// ...
run_refresh_stage!("ingest", ..., self.ingest_daily(refresh_from, refresh_to));
// ingest_daily 不接受 cb
run_refresh_stage!("indicators", ..., self.compute_indicators(cb));
// 其余阶段接受 cb
```

**问题**：`cb` 被构造出来但 `ingest_daily` 不接收 progress callback。这意味着刷新流程的第 1/7 阶段（通常也是最耗时的阶段之一）无法通过 callback 报告细粒度进度，只能通过外层的 `notify()` 收到 "[1/7] Starting ingest..." 一次消息。

**建议**：为 `ingest_daily` 添加可选的进度回调参数，或至少在当前阶段完成时通过 callback 报告 "ingest complete"，保持 7 个阶段的行为一致性。

### 7. `sync_and_export` 在需要刷新时完全不报告进度

**位置**：`crates/app-service/src/lib.rs`（`sync_and_export` 方法）

**问题**：`sync_and_export` 内部调用 `self.refresh_pipeline(to, scope, run_backtests, None, None, None)`，最后一个 `None` 是 `progress_callback`。这意味着当用户执行 `sync-and-export` 且系统判定需要自动刷新时，整个刷新过程对用户完全静默。

**影响**：CLI 用户在 `--quiet=false` 时只会看到 `[sync-and-export] Starting...` 和 `Done.`，中间可能持续数分钟的刷新没有任何输出。

**建议**：将 `sync_and_export` 的 progress 语义与 `refresh_pipeline` 桥接，或至少把 `notify` 消息打印到 stderr。

---

### 8. `wiremock` 被声明在 workspace 依赖中，但仅作为单个 crate 的 dev-dependency 使用

**位置**：`Cargo.toml`（workspace 层）

**问题**：`wiremock = "0.6"` 被添加到 `[workspace.dependencies]`，但查看 `crates/app-service/Cargo.toml` 可知它仅在 `[dev-dependencies]` 中使用。将其提升到 workspace 级别意味着所有 workspace member 都能解析它，增加无意义的依赖图宽度。

**建议**：将 `wiremock` 从 `[workspace.dependencies]` 中移除，仅在 `crates/app-service/Cargo.toml` 的 `[dev-dependencies]` 中直接声明版本。

### 9. `probe_keyring` 在 `NoEntry` 时返回 `true`，语义误导

**位置**：`crates/app-service/src/lib.rs`（`probe_keyring` 函数）

```rust
fn probe_keyring() -> bool {
    let entry = keyring::Entry::new(LLM_SERVICE_NAME, LLM_ACCOUNT_NAME);
    match entry.get_password() {
        Ok(_) => true,
        Err(keyring::Error::NoEntry) => true,  // <-- 这里
        Err(_) => false,
    }
}
```

**问题**：`NoEntry` 表示 keyring 可用但当前没有这条记录，函数返回 `true`（"可用"）。这在 `AppContext::new` 中用于决定是否打印 keyring unavailable warning：

```rust
if !probe_keyring() {
    eprintln!("WARN: OS keyring is unavailable...");
}
```

**影响**：如果 keyring daemon 正常运行但用户从未设置过密码，`NoEntry` 返回 `true`，不会打印 warning。这本身是对的（keyring 可用）。但如果 keyring daemon 实际上**无法写入**（权限问题、沙箱环境），`set_password` 仍会在运行时失败并 fallback 到 SQLite，而这个 warning 只在构造时打印一次。

**建议**：将 `probe_keyring` 改为真正测试写入能力（例如尝试 set + delete 一个 probe 条目），或者重命名为 `probe_keyring_readable` 以避免误导。

## 低风险问题（LOW）

### 10. 部分单元测试仅验证字符串常量，无功能价值

**位置**：`crates/app-service/src/lib.rs` 测试模块

例如：
- `llm_system_prompt_contains_expected_content`
- `llm_user_prompt_includes_report_and_structured_request`
- `llm_missing_api_key_error_is_clear`

**问题**：这些测试断言的是硬编码字符串字面量包含某些子串。它们测试的是"常量有没有被意外修改"，而非业务逻辑。如果常量确实需要修改，这些测试会成为维护负担。

**建议**：将系统 prompt 和 error message 模板提取为 crate-level 常量（若尚未提取），删除仅验证字面量的测试，保留有真实行为验证的测试（如 mock server、round-trip serde、error propagation）。

## 正面评价

以下方面做得好，值得保持：

1. **CLI `--quiet` 标志设计一致**：所有新增和改造的命令都正确检查了 `cli.quiet`，progress 统一走 stderr，不污染 stdout JSON 输出。
2. **LLM 错误消息不泄露 API key**：mock server 测试明确验证了 401/429/500 错误消息中不包含 secret key。
3. **sync-and-export 的 gate 检查逻辑正确**：`sync_gate_needs_refresh` + `validate_sync_refresh_result` 的组合避免了在刷新失败时继续导出旧报告。
4. **新增 AGENTS.md 补齐了缺失引擎 crate**：`backtest-engine`、`indicator-engine`、`rotation-engine`、`signal-engine`、`strategy-engine` 都有了就近约束文档。
5. **progress metadata 从桌面端下沉到 app-service**：`pipeline_stages` 模块让 CLI 和桌面端共享同一套阶段定义和进度数值，消除了此前两端各自维护的不一致风险。
