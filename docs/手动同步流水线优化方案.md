# 手动同步流水线优化方案

> **文档定位**：活跃设计参考
>
> 本文档用于分析当前 README / CLI 手动同步链路为什么会出现“需要跑 2–3 次才把默认最新日期推进到较新日期”的体验问题，并给出短中期优化方案。
>
> 当前运行中的真实行为仍以以下文档和代码为准：
>
> - `README.md`
> - `docs/系统架构与数据流.md`
> - `docs/功能模块与处理逻辑.md`
> - `docs/日常操作手册.md`
> - `apps/cli/src/main.rs`
> - `crates/app-service/src/lib.rs`
> - `crates/market-store/src/lib.rs`

---

## 1. 文档目标

本文档聚焦一个非常具体的现象：

> 用户按 README 中的手动命令执行数据同步与计算，有时需要连续执行 2–3 次，dashboard / export 的默认最新日期才会推进到较新的日期。

本文档的目标不是立即修改实现，而是先回答三件事：

1. **当前这组手动命令的真实逻辑是什么**
2. **为什么用户会产生“要多跑几次”的体感**
3. **在不直接上重型架构改造的前提下，哪些优化最值得优先做**

---

## 2. 当前问题定义

## 2.1 用户看到的问题

当前 README 暴露的 CLI 手动链路是：

```bash
cargo run -p quant-cli -- ingest-daily --from <date> --to <date>
cargo run -p quant-cli -- compute-indicators
cargo run -p quant-cli -- compute-macro --from <date> --to <date>
cargo run -p quant-cli -- compute-rotation
cargo run -p quant-cli -- compute-strategy-preferences
cargo run -p quant-cli -- compute-signals
cargo run -p quant-cli -- pipeline-dates
cargo run -p quant-cli -- check-data-health
cargo run -p quant-cli -- dashboard-snapshot
cargo run -p quant-cli -- export-report
```

用户的直觉通常是：

- 先把行情同步到新日期
- 再顺序跑完整条链路
- 最终 dashboard / export 默认最新日期应该同步推进

但现实中可能出现：

1. `daily_bar` 已经到了新日期
2. 中间若干阶段也看起来执行成功
3. `dashboard-snapshot` / `export-report` 默认最新日期却仍停留在旧日期
4. 再跑一遍，日期才前进

这会让用户形成一种体验：

> **系统不是“一次刷新”，而像“多次碰运气推进”。**

## 2.2 这不是单点 bug，而是链路抽象不一致

当前更像是一个**产品抽象与工程抽象不一致**的问题：

- README 暴露给用户的是：
  - 一组工程式分步命令
- dashboard / export 对“最新日期”的判断是：
  - 一个产品级最终可用门控结果

也就是说：

- **前者是松耦合阶段链**
- **后者是强门控最终产物**

这两层之间缺少一个真正的“全链路完成并通过资格检查”的中间抽象。

---

## 3. 当前实现逻辑梳理

## 3.1 CLI 只是逐条转发，不做统一编排

`apps/cli/src/main.rs` 当前只是把每个命令逐条转发到 `AppContext`：

- `ingest-daily` -> `ingest_daily(...)`
- `compute-indicators` -> `compute_indicators()`
- `compute-macro` -> `compute_macro_regime(...)`
- `compute-rotation` -> `compute_rotation()`
- `compute-strategy-preferences` -> `compute_strategy_preferences()`
- `compute-signals` -> `compute_signals()`
- `pipeline-dates` -> `pipeline_date_diagnostics_with_scope(...)`
- `dashboard-snapshot` -> `dashboard_snapshot_with_scope(...)`
- `export-report` -> `export_report_with_scope(...)`

这意味着 CLI 当前没有一个真正的：

- `refresh-all`
- `sync-and-compute`
- `run-pipeline-until-available-date-advances`

之类的聚合命令。

## 3.2 每个阶段的真实依赖关系

当前阶段依赖大体是：

1. `ingest-daily`
   - 为各 symbol 抓取并写入 `daily_bar`
2. `compute-indicators`
   - 读取 `daily_bar`，重建 `indicator_snapshot`
3. `compute-macro`
   - 抓取/复用宏观历史，写入：
     - `macro_snapshot`
     - `market_regime`
     - `environment_snapshot`
4. `compute-rotation`
   - 基于 `daily_bar` 写入 `rotation_rank`
5. `compute-strategy-preferences`
   - 读取：
     - `daily_bar`
     - `indicator_snapshot`
     - `market_regime`
     - `rotation_rank`
   - 写入 `strategy_preference`
6. `compute-signals`
   - 读取：
     - `strategy_preference`
     - `market_regime`
     - `rotation_rank`
   - 写入 `signal_snapshot`

也就是说，后面的阶段并不是“只要前一步成功就自动代表结果已经可用于 dashboard/export”。

## 3.3 默认最新日期的资格门槛远高于“行情已同步”

`dashboard_available_dates_for_scope()` 当前会对一个日期做非常严格的资格判断。

一个日期只有同时满足以下条件，才会进入 dashboard/export 的默认最新日期集合：

1. `signal_snapshot` 的 scoped entity count >= expected_count
2. `rotation_rank` 的 scoped entity count >= expected_count
3. 对应 scope 在该日期 **on or before** 可取到 `market_regime`
4. 对应 scope 在该日期 **on or before** 可取到 `environment_snapshot`

少任一项，这个日期就不会被认为是“最新可分析日期”。

这里要特别注意：

- `signal_snapshot` / `rotation_rank` 更接近“该日期上的覆盖资格”
- `market_regime` / `environment_snapshot` 更接近“该日期截至当时是否已有可用 as-of 结果”

因此这四项虽然共同构成 gate，但并不是完全同一种“同日逐表存在性检查”。

因此当前默认最新日期实际不是：

> `daily_bar` 最新日期

而是：

> **一个已经通过 signal + rotation + regime + environment 四重资格门控的最终日期**

---

## 4. 为什么用户会感觉“要跑 2–3 次”

## 4.1 根因 1：前台暴露的是分步命令，后台判断的是最终产物资格

用户执行的是工程链路：

- 抓数据
- 算指标
- 算宏观
- 算轮动
- 算策略
- 算信号

但系统对“是否前进到新日期”的判断是在链路末端才发生，而且判断标准远强于“前面都跑过一遍”。

于是会出现一种错位：

- 从执行视角看：
  - “我都跑完了”
- 从资格视角看：
  - “这个新日期还不够格进入 dashboard/export 默认日期”

## 4.2 根因 2：latest-date gate 是 completeness gate，不是 existence gate

当前 gate 不只是检查有没有行，而是检查：

- 对 scope 内 `latest_gate_required == true` 的标的，
- 新日期是否已经在 `signal_snapshot` / `rotation_rank` 上**足量覆盖**

因此只要：

- 某个 gate-required instrument 缺了一天信号
- 或 rotation 没完全补齐

那么这个日期就会被整个排除。

这很容易让用户产生误解：

- 实际上是“新日期不完整”
- 体感上却像“系统没同步上去”

## 4.3 根因 3：链路是阶段式重算生产表，而不是一次运行的发布模型

当前多个阶段写入采用的是：

- `ALTER TABLE ... DELETE WHERE ...`
- 然后 `INSERT`

并且直接作用于生产表。

虽然当前 delete mutation 已通过 `mutations_sync = 1` 同步等待，避免了旧的异步删除问题，
但整条链仍然是：

> **阶段式重算生产表，而不是“本次运行先生成 staging，再一次性 promote”。**

因此：

- 某次运行前半段可能已经写入新数据
- 但最后没通过 default latest-date gate
- 用户下一次再跑时，又从新的中间状态继续推进

用户看到的就不是：

- “上次失败，这次重新发布成功”

而更像：

- “我多跑了一次，终于推进了”

## 4.4 根因 4：当前最明确的 fail-loud 只收口在 signal 这一段

当前系统已经对最危险的一类情况加了防护：

- 当 `strategy_preference` 新于 `signal_snapshot` 时
- 或 `signal_snapshot` 最新日 coverage 不完整时
- `compute-signals` / desktop refresh 会 fail loud

这已经大幅降低了“假成功态”。

但问题仍然没有完全消失，因为：

- `dashboard_available_dates` 的最终资格门槛不只包含 signal
- 还包含 `rotation_rank` / `market_regime` / `environment_snapshot`

因此 signal guard 虽然很有价值，但它并没有把“整条链是否已经形成新的可分析日期”抽象成一个完整的一次性判断。

---

## 5. 当前实现中已经存在的优点

在讨论优化前，先明确当前实现并不是“完全没有防护”。

当前已经具备：

1. `pipeline-dates`
   - 可以查看每个 stage 是否 lagging
   - 可以查看最新日是否 complete
2. `PipelineDateDiagnostics.alerts`
   - 已能对 signal-vs-strategy 错位给出明确提示
3. `compute-signals` fail loud
   - 阻止最危险的 stale signal 假成功
4. desktop refresh consistency alerts
   - 已在桌面默认路径中补了 end-state consistency check

也就是说，系统不是完全盲跑，而是：

> **已经具备局部诊断和局部 fail-loud，但还缺少一个面向 CLI 用户的完整 latest-gate 解释与一次性全链路完成抽象。**

---

## 6. 优化目标

围绕这个问题，优化目标不应该定义成“让所有命令都自动重试”，而应该定义成：

1. **让用户把它理解为一次刷新，而不是一串工程命令**
2. **让系统在一次运行结束时明确告诉用户：最新日期为什么没推进**
3. **尽量减少用户手工重复执行整条链路的必要性**
4. **在不立刻引入重型架构改造的前提下，先把体验修顺**

---

## 7. 优化方案分层

## 7.1 方案 A：新增 CLI 聚合命令（最高优先级）

### 决策建议

新增一个真正面向用户语义的聚合命令，例如：

```bash
cargo run -p quant-cli -- refresh-all --to 2026-04-26
```

或者：

```bash
cargo run -p quant-cli -- sync-and-compute --to 2026-04-26
```

这里要明确：

- 这条命令服务于 **工程 / 高级用户路径**
- 它的目标是把当前 README 里的分步 CLI 路径变得更像“一次刷新动作”
- 它**不替代**桌面端 `Refresh data` 作为默认用户路径

### 它应该做什么

这个命令内部直接串行调用：

1. `ingest_daily`
2. `compute_indicators`
3. `compute_macro_regime`
4. `compute_rotation`
5. `compute_strategy_preferences`
6. `compute_signals`
7. 可选：`refresh_backtests_for_standard_scopes`
8. 最后自动运行：
   - `pipeline_date_diagnostics_with_scope(...)`
   - 汇总当前 default latest date 是否推进

### 它最重要的价值

不是少打一串命令，而是：

> **把“工程阶段链”收敛成“一个有最终结果判定的刷新动作”。**

### 为什么这是最高优先级

因为它：

- 改动面相对可控
- 不需要立即改底层存储模型
- 能直接消除 README 当前暴露给用户的抽象错位

但要注意：

> **聚合命令本身不能单独视为完整 Phase 1。**
>
> **如果它没有在结束时明确解释 latest-date gate 是否推进、为什么没有推进，那它本质上只是减少了用户输入命令的次数，而没有真正解决核心困惑。**

## 7.2 方案 B：把 end-state 解释做成命令输出，而不是让用户自己猜

这不是一个“可以晚很多再补”的附属增强，而应和 CLI 聚合命令一起视为**第一阶段的一体交付**。

当前用户需要自己跑：

- `pipeline-dates`
- `check-data-health`
- `dashboard-snapshot`

然后自己推断：

- 到底是哪里没追平
- 是否只是 signal 落后
- 还是最终 latest-date gate 没过

建议聚合命令在结束时直接输出：

1. freshest market date
2. dashboard latest available date
3. 每个 scope 的 gate 是否推进
4. 哪个 stage lagging / incomplete
5. 如果没推进，推荐的下一步是什么

例如：

```text
Refresh finished, but latest available date did not advance.

Freshest market date: 2026-04-26
Latest available dashboard date: 2026-04-24

Blocking stages:
- signal_snapshot (CN): incomplete on 2026-04-26 (18/21)
- rotation_rank (HK): lagging by 1 day
- market_regime (GLOBAL): no usable as-of row for the candidate date window

Recommended next step:
- rerun compute-signals after checking missing gate instruments
```

### 价值

这会把当前“多跑一遍试试”变成：

> **系统明确解释为什么没有前进。**

## 7.3 方案 C：增加 gate explanation 专用命令

在 `pipeline-dates` 基础上，可以进一步新增一个更面向结果资格的命令，例如：

```bash
cargo run -p quant-cli -- explain-latest-gate
```

专门回答：

- freshest market date 是多少
- latest available dashboard date 是多少
- 哪个 scope 没推进
- 具体卡在：signal / rotation / regime / environment 哪一项
- gate-required instruments 里哪些 symbol 缺失

### 价值

这比通用的 `pipeline-dates` 更接近用户真正的问题：

> “为什么默认最新日期还没上去？”

## 7.4 方案 D：减少重复全量重跑，提供更明确的增量编排

当前 README 里用户更像是在做“整段链路重跑”。

可以考虑后续增加更明确的增量策略，例如：

- `compute-indicators` 支持基于最新 indicator 日期回推缓冲区重算
- `compute-rotation` 支持类似 latest-date aware 的增量入口
- `compute-strategy-preferences` / `compute-signals` 支持 latest-date aware 的增量区间编排

### 但这里要注意

这不是第一优先级，因为：

- 它的实现复杂度高于聚合命令
- 也更容易引入边界错误

更合理的顺序是：

1. 先做聚合命令 + end-state explanation
2. 再做更聪明的增量编排

---

## 8. 中长期方案

## 8.1 staging / run_id / promote 模型

如果从根上解决“多跑几次才推进”的体验，最终方向仍然是：

1. 每次刷新有独立 `run_id`
2. 各阶段先写 staging 或 run-scoped 数据
3. 只有当 end-state checks 全部通过时，才 promote 为当前默认最新版本

这会把当前模型从：

- 阶段式重算生产表

变成：

- 一次刷新生成一组候选结果
- 通过资格检查后再正式发布

### 好处

这样用户看到的就会变成：

- “这次刷新成功并发布”
或
- “这次刷新失败，旧版本保持不动”

而不是现在的：

- “有些阶段似乎已经写了，但默认最新日期没推进，我再跑一遍看看”

## 8.2 为什么不建议现在立刻做

因为它会明显放大改动范围：

- ClickHouse 表模型
- 读取路径
- dashboard/export 的 latest version 语义
- refresh / CLI / report registry 的一致性逻辑

所以它更适合作为：

> **中长期方向，而不是当前第一刀。**

---

## 9. 推荐实施顺序

## 9.1 第一阶段（应优先做）

1. 新增 CLI 聚合命令：`refresh-all` / `sync-and-compute`
2. 命令结束时自动输出 end-state diagnostics
3. 明确告诉用户 latest-date 是否推进，以及阻塞原因

也就是说，第一阶段真正的最小完整交付是：

> **CLI 聚合刷新命令 + latest-date gate 解释输出**

而不是只做前者。

### 预期收益

- 最快改善用户“为什么还没到最新日期”的困惑
- 把 README 暴露给用户的接口从“工程链路”升级成“产品动作”

## 9.2 第二阶段（紧随其后）

1. 新增 `explain-latest-gate`
2. 输出 per-scope gate 详情
3. 输出缺失 gate instruments / blocking stage

### 预期收益

- 降低排障成本
- 让 CLI 用户也获得接近 desktop refresh consistency 的解释体验

## 9.3 第三阶段（再往后）

1. latest-date aware 增量编排
2. 更少的整段重算
3. 更明确的 partial rerun 入口

## 9.4 第四阶段（中长期）

1. run_id / staging / promote
2. 真正的一次运行发布模型

这一阶段应被视为：

- 在完成前几阶段之后，
- 如果用户仍然持续遇到“部分阶段已写入，但默认最新日期语义仍有明显歧义”的问题，
- 再进入的中长期升级方向。

---

## 10. 与现有方向的关系

这份优化方案和当前已经确认的方向是一致的：

- `desktop refresh` 仍然是默认用户路径
- CLI 聚合命令是对工程/高级用户路径的补强，不是替代桌面端
- 当前已存在的 `Retry failed stage` / `Run from stage` 继续保留
- 当前已存在的 signal fail-loud / diagnostics alerts 继续作为底层一致性基础

也就是说，这不是一次“推翻现有刷新语义”的提案，而是：

> **在现有 trust / diagnostics / refresh consistency 基础上，把 CLI 路径也升级成更像“一次完整刷新动作”的抽象。**

---

## 11. 一句话结论

> **当前需要优化的不是单个计算函数本身，而是“README 暴露给用户的是分步工程链路，而系统判断最新日期的是强门控最终产物”这层抽象错位。**
>
> **第一优先级应该是新增 CLI 聚合刷新命令，并在结束时明确解释 latest-date gate 是否推进以及为什么没有推进。**
