# 系统架构与数据流

本文档用于梳理当前项目的**整体架构**、**数据来源**、**数据流转路径**与**关键日期语义**。

---

## 1. 系统定位

`rust-quant-analysis-system` 是一个面向 **指数 / ETF、低频、趋势、长线** 的本地桌面量化研究系统。

当前系统目标不是做：

- 高频执行
- 自动下单
- 多用户在线服务

当前系统目标是：

- 采集日线数据
- 生成技术指标
- 结合宏观环境、轮动强弱、策略偏好生成信号
- 做基础回测
- 导出报告
- 在桌面端展示结果

## 3. 数据来源

### 3.1 行情数据

#### CN 指数 / ETF

- **主源**：Eastmoney
- **兜底**：Tencent

#### HK 指数

- **主源 / 组合源**：Eastmoney + Tencent

#### 当前不作为默认主源

- Yahoo Finance
- Tushare

说明：

- 当前运行环境里，Yahoo Finance 在历史接口上出现过 `403`
- Tushare 没有作为当前 V1 默认依赖
- universe 现在区分：
  - `enabled=true`：仍属于研究 universe
  - `latest_gate_required=true/false`：是否参与“最新 dashboard/report 可用日期”的完整性门槛
- 这意味着某些已知 provider 不稳定但仍有研究价值的标的（例如部分跨市场连接类指数）可以继续保留在 universe 中，但不再永久阻塞 GLOBAL/HK 最新报告

### 3.2 宏观数据

- 来源：**FRED**
- 当前使用的核心因子：
  - `VIXCLS`
  - `DGS10`
  - `DTWEXBGS`
  - `DFF`

说明：

- 当前机器上 FRED 抓取支持：
  - `reqwest` 主路径
  - Windows 下 `curl.exe` fallback
- **当前版本更新**：FRED 获取改为可配置开关（`config/fred.toml`）
  - `enabled = true`：通过 FRED API 获取（`api.stlouisfed.org/fred`）
  - `enabled = false`：使用 ClickHouse 已存宏观数据，跳过 HTTP 获取
  - API Key 在 `config/fred.toml` 中管理，支持环境变量插值（`${FRED_API_KEY}`）
  - 限流：500ms 请求间隔，遵守 FRED API 120 次/分钟限制
  - 无配置时默认 `enabled = true`，但缺失 API Key 会提示用户创建配置文件
- CLI 命令：`set-fred-config` / `show-fred-config`

## 5. 核心数据流

### 5.1 行情采集与存储

入口：

- `AppContext::ingest_daily`

流程：

1. 从 `config/universe.json` 读取标的池
2. 对每个标的调用 `fetch_daily_bars`
3. `fetch_daily_bars` 内部按顺序：
   - Eastmoney
   - 失败时 Tencent fallback
4. 每根 bar 进入 `normalize_daily_bar()`
5. 持久化进入 ClickHouse `daily_bar`

输出表：

- `instrument`
- `daily_bar`

### 5.2 指标计算流

入口：

- `AppContext::compute_indicators`

输入：

- `daily_bar`

处理：

- `MA10 / 20 / 30 / 60 / 120`
- `EMA12 / EMA26`
- `MACD / signal / hist`
- `RSI14`
- `ATR14`
- `VOL_MA20 / VOL_MA60`

输出表：

- `indicator_snapshot`

### 5.3 宏观与 regime 计算流

入口：

- `AppContext::compute_macro_regime`

输入：

- FRED 因子序列
- CN anchor：`000300`
- HK anchor：`HSI`

处理分三层：

#### 第一层：`macro_snapshot`

把宏观因子转成：

- `factor_value`
- `factor_score`

#### 第二层：`market_regime`

结合：

- 宏观因子
- CN / HK anchor 趋势打分

输出为真正的 per-scope regime：

- `GLOBAL`
- `CN`
- `HK`

每个 scope 独立产出：

- `trend_score`
- `liquidity_score`
- `risk_score`
- `regime_label`
- `macro_as_of_date`

#### 第三层：`environment_snapshot`

结合：

- scoped regime
- watchlist breadth proxy
- volume / turnover participation proxy

输出：

- `breadth_pct`
- `breadth_pct_sma5`
- `breadth_5d_delta`
- `breadth_state`
- `liquidity_proxy_score`
- `stress_proxy_score`
- `environment_score`
- `environment_label`

### 当前 regime 特性

系统已经改成：

> **宏观因子按最近可用值向后延用（forward-fill / as-of）**

为保证这个语义在你手动跑窄窗口时也成立，`compute_macro_regime(from, to)` 当前会：

1. 向前多取一段宏观历史（lookback buffer）
2. 在这段完整历史上构建 `macro_snapshot / market_regime / environment_snapshot`
3. 最后只把 `[from, to]` 区间内的结果写回数据库

所以：

- `report_date` 可以是最新分析日
- `regime_as_of_date` 保留真实宏观参考日期
- `regime_stale_days` 显示滞后天数

### 运行期容错语义

`compute_macro_regime(from, to)` 现在不是“本次外部抓取失败就直接清空该窗口宏观层”，而是：

1. 先尝试抓取最新 FRED 因子
2. 把成功抓到的因子写回 `macro_snapshot`
3. 同时读取库里已持久化的 `macro_snapshot` 历史
4. 用“已持久化历史 + 本次成功抓到的新因子”一起重建 `market_regime / environment_snapshot`

这意味着：

- 某个 FRED 因子短时异常时，系统仍可用最近一次成功写入的宏观历史做 as-of forward-fill
- 只有当某个宏观分组（风险组 / 流动性组）完全没有任何可用历史时，才会退化到更保守的中性分数
- provider 异常会进入 `failed_items`，但不会再静默把 scoped regime / environment 整段打空

输出表：

- `macro_snapshot`
- `market_regime`
- `environment_snapshot`

### 5.4 轮动计算流

入口：

- `AppContext::compute_rotation`

输入：

- `daily_bar`

处理：

- 计算 `RS20 / RS60 / RS120`
- 合成 `momentum_score`
- 按交易日横截面排名

输出表：

- `rotation_rank`

Dashboard 展示：

- `Leaders`
- `Laggards`

### 5.5 策略偏好计算流

入口：

- `AppContext::compute_strategy_preferences`

输入：

- `daily_bar`
- `indicator_snapshot`
- `market_regime`
- `rotation_rank`

当前语义：

- 这一层当前会按 `GLOBAL / CN / HK` 构建对应分析上下文
- 输出会显式携带 `analysis_scope` 与 `regime_basis_scope`

当前四类策略：

- `VALUE_LEFT`
- `TREND_PULLBACK`
- `TREND_BREAKOUT`
- `MOMENTUM_RIGHT`

输出表：

- `strategy_preference`

### 5.6 最终信号计算流

入口：

- `AppContext::compute_signals`

输入：

- `strategy_preference`
- `market_regime`
- `rotation_rank`

当前语义：

- `signal_snapshot` 当前会显式携带 `analysis_scope` 与 `regime_basis_scope`
- dashboard / report / frontend 需要结合这些 provenance 一起解释 signal，而不是只根据当前 dashboard scope 直接推断

输出：

- `final_score`
- `signal_label`
- `explanation`

输出表：

- `signal_snapshot`

Dashboard 展示：

- `Bullish opportunities`
- `Defensive / sell watch`

### 5.7 回测流

入口：

- `AppContext::run_backtest`

输入：

- `signal_snapshot`
- `daily_bar`

处理方式：

- 多头组合
- 次日开盘成交
- 手续费 / 滑点
- 最大持仓数约束

输出表：

- `backtest_run`
- `backtest_trade`
- `backtest_equity_curve`

当前用户面语义：

- 最新 backtest 会暴露 `analysis_scope`、`signal_scope`、`regime_basis_scope`
- dashboard / report 还会显式标出它是否 `matches current snapshot`

### 5.8 报告与 Dashboard 流

入口：

- `AppContext::dashboard_snapshot`
- `AppContext::export_report`
- `AppContext::export_data_health_report`

输入：

- `market_regime`
- `environment_snapshot`
- `rotation_rank`
- `signal_snapshot`
- `backtest_run`
- `data_health_summary`

输出：

- `DashboardSnapshot`
- `PipelineDateDiagnostics`
- Markdown 日报
- Markdown 数据健康报告

输出表 / 文件：

- `report_snapshot`
- `reports/daily-report-*.md`
- `reports/data-health-*.md`

其中：

- `daily-report-*.md` 的日期对应 `report_date`
- `data-health-*.md` 的日期对应 **本次检查覆盖到的 freshest market date**，不是导出瞬间的 wall-clock 日期

### 5.9 V3 sync-and-export 流（一键同步导出）

入口：

- `AppContext::sync_and_export`

流程：

1. 若显式传了 `--date`，跳过自动刷新，直接导出该日期报告
2. 若未传 `--date`：
   - 调用 `explain_latest_gate(scope)` 检查 gate 状态
   - 若 gate 已推进到最新，直接导出
   - 若 gate 落后，自动调用 `refresh_pipeline()` 进行全链路刷新
   - 刷新完成后再次检查 gate
   - 若 gate 仍落后，fail-loud 报错退出
   - 若 gate 推进成功，导出报告
3. 返回 JSON 包含报告路径、刷新状态、gate 信息

说明：

- 这是 V3 新增的**推荐默认 CLI 路径**
- 一条命令完成：检查 → 刷新（如需要）→ 导出
- Progress 输出到 stderr，stdout 保持纯 JSON

### 5.10 V3 LLM 分析流（大模型报告分析）

入口：

- `AppContext::analyze_report_with_llm`

流程：

1. 从 SQLite `app_config` 读取 LLM 配置（base_url / model / timeout）
2. 从 OS keyring 或 SQLite `credential_store` 读取 API Key
3. 通过 `dashboard_snapshot_with_scope()` 获取快照，用 `render_markdown_report()` 生成报告 Markdown
4. 构建 prompt：system 消息（量化分析师角色）+ 报告内容 + 请求分析解读
5. 调用 OpenAI-compatible API（同步阻塞）
6. 保存响应到 `reports/llm-analysis-{scope}-{date}.md`
7. 注册到 `report_snapshot` 表，可被桌面端 Recent Reports 识别

安全约束：

- API Key 绝不出现在 stdout、stderr、日志、错误信息、JSON 输出或测试快照中
- 前端/桌面端不接触 API Key，仅在 Rust CLI / app-service 层处理
- API Key 优先存储在 OS keyring，keyring 不可用时回退到 SQLite（明文，有警告提示）

## 7. 关键日期语义

### `Selected analysis date`

当前正在查看的分析日期。

### `Latest available analysis`

当前系统可供选择的最新分析日期。

它本质上由下游可用链路共同决定，当前至少要求：

- `signal_snapshot` 有数据
- `rotation_rank` 同日有数据
- `market_regime` 存在不晚于该日的 regime
- `environment_snapshot` 存在不晚于该日的 environment

### `Regime as-of date`

当前 dashboard 实际采用的宏观环境日期。

### `Scope`

当前 dashboard / report 的观察视角：

- `GLOBAL`
- `CN`
- `HK`

需要注意：

> `dashboard/report` 当前已按 scope 读取 regime / environment；signal / backtest 则需要继续结合它们自己的 provenance（如 `analysis_scope` / `regime_basis_scope` / `matches current snapshot`）一起理解，而不是只按当前 dashboard scope 直接推断。

### `regime_stale_days`

分析日期与宏观环境日期之间的滞后天数。

这通常表示：

- 行情 / 指标 / 信号已经更新到最新交易日
- 但宏观观测值本身的发布时间更慢

因此：

> `report_date` 新，不代表 `regime_as_of_date` 也必须同样新。

### `Pipeline freshness`

这是当前用于排查“日期是否到了、最新日是否完整”的第一诊断层。

它会同时给出：

- `latest_date`
- `lag_days`
- `is_latest`
- `latest_entities`
- `expected_entities`
- `is_complete`

需要注意：

> **`is_complete` 不能单独看，必须和 `is_latest` / `lag_days` 一起看。**

因为一个 stage 可能：

- 对它自己的 `latest_date` 来说是完整的
- 但它整体仍然落后于 freshest market date

## 8. 数据健康检查流

入口：

- `AppContext::check_data_health`

当前检查项：

- 主源可达性
- fallback 可达性
- 缺口
- 异常大波动
- 缺失 turnover
- FRED 宏观源 transport（`reqwest` / `curl` / `failed`）
- freshest market date 的 symbol 覆盖情况

输出：

- `DataHealthSummary`
- Markdown 报告
- Dashboard 数据健康面板

当前新增字段：

- `freshest_market_date`
- `symbols_on_freshest_market_date`
- `symbols_missing_freshest_market_date`
- `freshest_market_date_complete`

这层检查回答的是：

> **最新市场日期这一天，标的池是不是全量落库了。**

它和 `Pipeline freshness` 的区别是：

- `Pipeline freshness` 更偏 stage 级别
- `Data health` 更偏 symbol/provider 级别

## 11. V8 Research Asset Workspace 数据流

> **V8 新增**：在 V7 Research Platform 下游新增 durable Research Asset 层。V6/V7 平台语义不变，只在其输出之上做资产持久化与索引。

### 11.1 在总体架构中的位置

V8 位于 `crates/app-service` 内部，与报告生成、健康检查、刷新编排并列，但只处理研究产物（Evidence / Snapshot）的持久化：

```text
V7 Research Platform（已冻结）
  ├─ V6 Observation Layer  ← research-srd / research-stretch / research analytics
  ├─ V7.1 Market Evolution  ← research confirmation / recovery
  ├─ V7.2 Historical Evidence  ← research analogues / calibration
  └─ V7.3 Research Synthesis  ← research consensus
           ↓
  crates/app-service::workspace
           ↓
  workspace/
    ├─ evidence/                  ← Evidence Asset（RA-XXXXXX）
    │   ├── replay/               ← Historical Replay 批量产出
    │   └── analytics/            ← research analytics --save-evidence 产出
    ├─ snapshots/                 ← Snapshot Asset（RA-XXXXXX）
    │   └── 引用 EvidenceRef { id, version }
    └─ registry/
        ├─ evidence-index.json    ← 统一索引：id, kind, version, scope, state, hashes
        └── snapshot-index.json   ← 统一索引：id, kind, version, scope, state, refs
```

### 11.2 Evidence 资产流

入口：

- `AppContext::research_condition_evidence`（通过 `crates/app-service/src/research_evidence.rs`）
- `AppContext::research_analytics`（带 `--save-evidence` 时）
- Historical Replay 脚本（`shadow-production/historical-replay/run-historical-replay.ps1`）

流程：

1. 从 ClickHouse 读取条件发生日的数据（`signal_snapshot`、`rotation_rank`、`market_regime`、`daily_bar`）
2. 由 `research_evidence` 计算条件匹配与前向收益（median / mean / best / worst / positive ratio / median max drawdown）
3. 生成 `Evidence` 结构体，包含 `dataset_hash` 与 `config_hash`
4. 分配统一身份 `RA-XXXXXX`（`AssetKind::Evidence`）
5. 写入 `workspace/evidence/analytics/` 或 `workspace/evidence/replay/`
6. 在 `workspace/registry/evidence-index.json` 中登记为 `Draft`

输出文件：

- `workspace/evidence/{subpath}/RA-XXXXXX.json`
- `workspace/registry/evidence-index.json`

### 11.3 Snapshot 资产流

入口：

- `AppContext::research_snapshot`（由 V7 orchestration 内部调用）
- 未来 CLI 命令可能直接保存 Snapshot

流程：

1. 收集当前研究上下文（scope、date、regime、signal、rotation、backtest 等）
2. 把相关 Evidence 的引用（`EvidenceRef { id, version }`）写入 Snapshot，而不是嵌入 Evidence 数据
3. 计算 `dataset_hash` 与 `config_hash`
4. 分配统一身份 `RA-XXXXXX`（`AssetKind::Snapshot`）
5. 写入 `workspace/snapshots/RA-XXXXXX.json`
6. 在 `workspace/registry/snapshot-index.json` 中登记

输出文件：

- `workspace/snapshots/RA-XXXXXX.json`
- `workspace/registry/snapshot-index.json`

### 11.4 统一生命周期

每个 Research Asset 从创建到归档经过以下状态：

```text
Draft → Verified → Published → Superseded → Archived
```

- **Draft**：由计算/重放直接产出，尚未审计
- **Verified**：通过自动审计（hash 一致、依赖存在、scope/date 有效）
- **Published**：进入稳定引用，可被 Snapshot 或其他下游消费
- **Superseded**：被新版本替代，但保留用于历史对比
- **Archived**：过期或不再活跃，但仍可回溯

状态转换当前由 `WorkspaceManager` 维护，P3 之前不引入自动化晋升规则；CLI 与脚本默认产出 `Draft`。

### 11.5 统一身份规则

- 所有 Research Asset 使用 `RA-XXXXXX` 作为主标识（6 位大写数字字母）。
- 类型由 metadata 中的 `AssetKind` 决定：
  - `AssetKind::Evidence`
  - `AssetKind::Snapshot`
- 未来扩展类型（如 `Knowledge`、`Validation`、`Hypothesis`）也会复用 `RA-XXXXXX` 与相同生命周期。
- 现有 `EV-` / `SN-` 前缀的资产被 grandfathered，但新资产不再使用。

### 11.6 与 V6/V7 平台的边界

核心约束：

- **V8 不修改 V6 Observation 的语义**：`research analytics` 加不加 `--save-evidence`，计算结果一致。
- **V8 不修改 V7 Research Synthesis 的语义**：`research consensus` 不依赖 workspace 是否存在。
- **V8 只消费 V7 输出**：Evidence 来自 V6/V7 计算，Snapshot 引用 Evidence。
- **P3 之前不引入 Evidence 权重**：V8 只负责格式统一、身份统一、生命周期统一、持久化与索引；权重设计在门限达到后才启动。

### 11.7 可复现性

每个 Research Asset 记录：

- `dataset_hash`：输入数据集合的 hash
- `config_hash`：配置参数的 hash
- `scope` / `date` / `created_at` / `version`
- 依赖 Evidence 的 `EvidenceRef`（Snapshot）

重新运行相同输入与配置时，应得到可对比的 `dataset_hash` 与 `config_hash`； Evidence 内容本身是否逐字节一致，取决于计算实现是否 deterministic。

## 12. 一句话概括

> **这是一个以 ClickHouse 为分析底座、以 Rust engine 为处理核心、以 Tauri + Vue 3 为展示容器的本地量化研究系统，支持中英双语国际化界面；V8 开始把研究产物持久化为可复现的本地 Research Asset。**

它的核心价值是：

- 把多来源数据统一到一条分析链中
- 把原始行情加工成可解释的研究结果
- 把健康检查、信号、回测、报告、UI 放在同一个闭环中
- 把研究产物（Evidence / Snapshot）沉淀为可审计、可版本化的资产，而不是一次性报告

## 10. V4.5 Research Layer — 只读叙事分析

V4.5 将原有的 Skill Framework 重构为**极简的只读叙事层**。没有 Agent Profile、没有 Skill Registry、没有技能路由、没有比较分析、没有历史记录。只有 5 个固定按钮，每个按钮对应一个不同的系统 prompt 角色，输出 Markdown 纯文本。

### 10.3 治理约束（ADR-074）

| 约束 | 说明 |
|------|------|
| 只读 | Research Layer 只解释、质疑、提供上下文，绝不创建信号、评分、排序或修改决策 |
| 无评分输入 | `build_snapshot_context` 只传 symbol + label + rank order，不传 score/RS/CAGR/Sharpe/MaxDD |
| Markdown 纯文本 | 禁止 JSON schema、confidence、score、ranking、probability |
| 90 天冻结 | 90 天内禁止新增 Pattern、前端面板、定时调度、Backtest v2、参数优化、性能声称 |
