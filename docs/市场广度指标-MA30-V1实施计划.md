# 市场广度指标 MA30：V1 实施计划

## 1. V1 目标

本次 V1 **不实现真实全市场股票 breadth**，而是先实现一个可立即落地、与当前仓库架构一致的版本：

> **Watchlist Breadth Proxy: % Above MA30**

中文建议名称：

- **观察池 MA30 以上占比**
- **观察池广度（MA30）**

它的定义是：

> 在当前 `config/universe.json` 配置的已启用观察池（当前为 `INDEX + ETF`）中，有多少标的的 `close > ma30`。

---

## 2. V1 明确边界

## 2.1 V1 要做什么

V1 只做以下内容：

1. 基于已有 `indicator_snapshot.ma30` 和 `daily_bar.close` 计算观察池 breadth proxy
2. 按 **CN / HK 分开** 展示，不把两地市场混成一个主指标
3. 在 **dashboard** 中新增 breadth 面板
4. 在 **markdown report** 中加入 breadth 段落
5. 支持与当前 dashboard 一样的 **历史日期切换**

## 2.2 V1 不做什么

V1 暂不做：

1. **真实全市场股票 breadth**
2. `InstrumentType::Stock` 扩展
3. 新增全市场个股数据源
4. breadth 参与 `signal` 总分
5. breadth 写入独立 ClickHouse 表
6. 使用 `<10%` / `<20%` 这类 stock breadth 极端阈值直接给当前 proxy 打标签

---

## 3. 为什么 V1 采用“按需计算”而不是新建表

当前系统已经具备：

- `daily_bar.close`
- `indicator_snapshot.ma30`
- 已启用观察池 universe
- 现成的 dashboard / report 查询链路

当前观察池规模很小（指数 + ETF，数量有限），因此 V1 最低风险路径是：

> **在 dashboard snapshot 构建时，按需从现有数据中派生 breadth proxy。**

这样做的好处：

- 不改 schema
- 不增加 refresh pipeline 的持久化步骤
- 不新增新的“状态同步”问题
- 与当前仓库的轻量 V1 目标一致

只有在后续出现以下情况时，再升级到独立表：

- 需要长期 breadth 历史序列查询
- 需要独立导出/回测 breadth 数据
- 需要个股 universe 扩容到数千只

## 4. V1 功能定义

## 4.1 输出指标

V1 每个市场（CN / HK）输出以下字段：

- `report_date`
- `market`
- `universe_label`
- `eligible_count`
- `above_count`
- `breadth_pct`
- `breadth_pct_sma5`
- `breadth_5d_delta`
- `range_low_60d`
- `range_high_60d`
- `range_position_60d`
- `status_label`

其中：

### `eligible_count`

当日满足以下条件的观察池标的数量：

- 标的已启用
- 有当日 `close`
- 有当日 `ma30`

### `above_count`

满足 `close > ma30` 的标的数量。

### `breadth_pct`

```text
above_count / eligible_count * 100
```

### `breadth_pct_sma5`

对 breadth 百分比序列做 5 个可用观察点的简单均值。

### `breadth_5d_delta`

```text
current_breadth_pct - breadth_pct_5_days_ago
```

### `range_position_60d`

以最近 60 个可用观察点的最小值/最大值为区间，计算当前位置：

```text
(current - min) / (max - min)
```

用于表达：

- 接近近期低位
- 位于近期中部
- 接近近期高位

---

## 4.2 V1 状态标签

V1 不使用“极端恐慌”“超跌极端”这类 stock breadth 语义。

建议使用更保守的 proxy 标签：

- `improving`
- `weakening`
- `weak`
- `neutral`
- `strong`
- `near_local_low`
- `near_local_high`

推荐使用以下**确定性优先规则**：

### 前置规则

- 若 `eligible_count == 0`：
  - `status_label = "unavailable"`
- 若 `range_position_60d` 不可得：
  - 跳过区间位置规则
- 若 `breadth_5d_delta` 不可得：
  - 跳过动量规则

### 正式优先级

1. 如果 `eligible_count == 0` → `unavailable`
2. 如果 `range_position_60d <= 0.20` → `near_local_low`
3. 如果 `range_position_60d >= 0.80` → `near_local_high`
4. 如果 `breadth_5d_delta >= 10.0` → `improving`
5. 如果 `breadth_5d_delta <= -10.0` → `weakening`
6. 如果 `breadth_pct < 35.0` → `weak`
7. 如果 `breadth_pct > 65.0` → `strong`
8. 其他情况 → `neutral`

### 返回值约束

V1 允许的 `status_label` 取值固定为：

- `unavailable`
- `near_local_low`
- `near_local_high`
- `improving`
- `weakening`
- `weak`
- `neutral`
- `strong`

注：

- 上述阈值是 **UI 解释阈值**，不是交易阈值。
- 后续可根据实际观察再校准。

## 5. 产品展示方案

## 5.1 Dashboard

在 dashboard 中新增一个独立面板：

- 标题：`Watchlist Breadth (MA30)`

面板内部分成两个区域：

1. `CN tracked universe`
2. `HK tracked universe`

每个区域展示：

- 当前占比（大数字）
- `above_count / eligible_count`
- `SMA5`
- `5d delta`
- `60d range position`
- 状态标签 pill

## 5.2 Report

在 markdown report 中新增一节：

- `## Watchlist Breadth (MA30)`

内容包含：

- CN breadth 当前值、SMA5、5d delta、状态
- HK breadth 当前值、SMA5、5d delta、状态
- 一句解释：这是观察池 proxy，不是全市场股票 breadth

## 6. 技术实现路径

## 6.1 推荐实现策略：直接并入当前 dashboard snapshot 构建链路

当前已有链路：

- `AppContext::dashboard_snapshot(...)`
- `report_engine::build_dashboard_snapshot(...)`
- Tauri `dashboard_snapshot(report_date)`
- 前端 `loadSelectedSnapshot()` → `render()`

因此 V1 推荐：

> 直接把 breadth proxy 作为 `DashboardSnapshot` 的一部分返回。

这样有 3 个好处：

1. 自动继承当前历史日期选择能力
2. 自动进入导出 report 链路
3. 不需要额外新增前端拉取时序

---

## 6.2 建议新增的数据结构

### `crates/report-engine/src/lib.rs`

新增：

- `WatchlistBreadthMarketSnapshot`
- `WatchlistBreadthSnapshot`

建议字段：

```text
WatchlistBreadthMarketSnapshot
- market: String            // CN / HK
- universe_label: String    // CN tracked universe / HK tracked universe
- eligible_count: usize
- above_count: usize
- breadth_pct: f64
- breadth_pct_sma5: Option<f64>
- breadth_5d_delta: Option<f64>
- range_low_60d: Option<f64>
- range_high_60d: Option<f64>
- range_position_60d: Option<f64>
- status_label: String

WatchlistBreadthSnapshot
- report_date: String
- markets: Vec<WatchlistBreadthMarketSnapshot>
- methodology_note: String
```

然后在 `DashboardSnapshot` 中增加：

- `watchlist_breadth: Option<WatchlistBreadthSnapshot>`

---

## 6.3 计算放在哪里

推荐放在：

- `crates/app-service/src/lib.rs`

新增内部 helper，例如：

- `compute_watchlist_breadth_snapshot(&self, report_date: NaiveDate) -> Result<Option<WatchlistBreadthSnapshot>>`

理由：

- 需要同时读取 universe、daily_bar、indicator_snapshot
- app-service 本来就是聚合层
- breadth proxy 更接近应用视图数据，而不是基础领域引擎

### 计算流程

1. 读取 universe
2. 只保留当前已启用标的
3. 根据 `instrument.market` 分成 CN / HK
4. 对每个 symbol：
   - 读取 `fetch_daily_bars(symbol)`
   - 读取 `fetch_indicator_snapshots(symbol)`
   - 按日期对齐到 `report_date`
   - 当日存在 `close` 与 `ma30` 时纳入 `eligible_count`
   - 若 `close > ma30`，则 `above_count += 1`
5. 为每个市场构建最近 60 个可用日期上的 breadth 序列
6. 计算：
   - `breadth_pct`
   - `breadth_pct_sma5`
   - `breadth_5d_delta`
   - `range_low_60d`
   - `range_high_60d`
   - `range_position_60d`
   - `status_label`

---

## 6.4 为什么 V1 不需要新增 market-store 查询接口

当前观察池规模很小，因此 V1 推荐直接复用现有接口：

- `fetch_daily_bars(symbol)`
- `fetch_indicator_snapshots(symbol)`

不必为了 V1 先新增：

- 按 symbol 批量取指标快照
- breadth 专用查询接口
- breadth 专用存储表

如果后续有性能问题，再在 V1.1 / V2 中优化为：

- `fetch_indicator_snapshots_for_symbols(...)`
- `fetch_daily_bars_for_symbols(...)`

## 8. 实施阶段拆分

## Phase 1：后端数据模型与聚合计算

目标：

- `dashboard_snapshot(...)` 返回 breadth 数据

输出：

1. `DashboardSnapshot` 新增 `watchlist_breadth`
2. app-service 能按 `report_date` 计算 breadth proxy
3. markdown report 中包含 breadth 内容

验收：

- CLI `dashboard-snapshot` 能看到 breadth 字段
- 导出 report 含 breadth 段落

## Phase 2：前端 UI 展示

目标：

- desktop dashboard 展示 breadth 面板

输出：

1. CN / HK breadth 双区域面板
2. 当前值、SMA5、5d delta、近期区间位置、状态
3. 明确 proxy 注释

验收：

- 默认最新日期显示 breadth
- 切换历史日期后 breadth 跟随更新
- 无数据时优雅降级

## Phase 3：校准与文案微调

目标：

- 让 UI 状态解释稳定可用

输出：

1. 状态标签微调
2. 近期区间 lookback 天数确认
3. report 文案解释优化

验收：

- 不出现“全市场 breadth”误导文案
- 不出现 stock breadth 专用极端阈值误用

命令：

预期：

  - `eligible_count`
  - `above_count`

  - `status_label`

## 10. 明确延期到 V2 的内容

以下内容明确不进入本次 V1：

1. `InstrumentType::Stock`
2. A 股全市场股票 universe
3. Tushare stock pipeline
4. breadth 独立 ClickHouse 表
5. breadth 专门 CLI 命令
6. breadth 纳入 `market_regime` 或 `signal` 评分
7. HK 主板普通股 breadth
8. 行业 breadth / 板块 breadth / 全 A breadth / A500 breadth 等真实股票广度体系

---

## 11. 最终建议

V1 最合理的实现策略是：

> **把 breadth 当成一个 dashboard/report 层的观察池参与度 proxy，按需从已有 indicator + daily bar 数据派生，不新增 schema，不修改主分析链路，不加入信号评分。**

这是当前仓库最小、最稳、最符合现状的实现路径。
