# 阶段性更新（2026-05-07）

本文档总结 2026-05-07 完成的 Trading-Aware 门控优化与 data-starved warning 落地成果。

---

## 1. 这轮工作的总目标

解决 CN/HK 跨市场休市差异导致的 GLOBAL dashboard 被卡住问题，并补上信号生成阶段的数据缺失告警能力。

---

## 2. 已完成的阶段性成果

### 2.1 新增 TradingCalendar 模块与静态 JSON 日历配置

**新增文件：**

- `crates/core-domain/src/calendar.rs`
  - `TradingCalendar` 结构体
  - `is_trading_day(market, date)` — 判断某市场某日是否开市
  - `trading_symbols` / `non_trading_symbols_count` — 过滤开市/休市标的
- `config/calendars/cn_holidays.json` — CN 2024-2027 法定节假日
- `config/calendars/hk_holidays.json` — HK 2024-2027 法定节假日

**这意味着：**

- 系统现在理解 CN 与 HK 的交易日历差异
- 休市日配置以静态 JSON 维护，易于人工校对和补录

### 2.2 Dashboard 门控逻辑改为 Trading-Aware Partial Coverage

**改造文件：** `crates/app-service/src/lib.rs`

核心变化：`dashboard_available_dates_for_scope`

- 之前：要求所有 scoped_symbols 在目标日期都有数据
- 现在：只要求该日期"期望交易"的 symbol 有数据

**效果：**

- 当 CN 开市、HK 休市时，HK 标的不计入 `expected_count`
- GLOBAL scope 可以正常推进到 CN 的最新交易日，而不再被 HK 休市卡住

### 2.3 Pipeline 诊断同步改为期望感知

**改造文件：** `crates/app-service/src/lib.rs`

`pipeline_date_diagnostics_for_scope` 的 completeness check 现在同样只检查开市 symbol：

- `signal_snapshot` / `strategy_preference` / `rotation_rank` / `market_regime` 各阶段的 `is_complete` 都使用 `trading_symbols`
- 休市 symbol 的缺失不再导致 `is_complete = false`

### 2.4 TrustSummary 增加 non-trading 提示

**改造文件：** `crates/app-service/src/lib.rs`

`build_trust_summary` 现在会：

- 计算 `non_trading_count`（休市标的数量）
- 在 `notes` 中提示用户：
  > "2 symbol(s) were on non-trading markets on the freshest market date and were excluded from coverage checks."

**效果：**

- 用户能清楚看到为什么 GLOBAL 推进了但部分市场未参与
- 前端 `renderTrustSummaryPanel` 会自动显示这些 notes

### 2.5 数据健康检查过滤全休市期间的 gap

**改造文件：** `crates/app-service/src/lib.rs`

`analyze_gap_metrics` 现在接收 `instrument` 和 `calendar`：

- 检查 gap 期间是否**全部**为休市日
- 全休市 gap 不视为数据缺口（不会触发告警）
- gap 期间存在开市日但无数据，仍按 12 天阈值告警

**效果：**

- 黄金周 7 天 gap 不会再被误判为数据问题

### 2.6 signal-engine 增加 data-starved warning

**改造文件：**

- `crates/signal-engine/src/lib.rs`
- `crates/app-service/src/lib.rs`
- `crates/core-domain/src/lib.rs`（新增 `SignalBuildStats`）

`build_signal_snapshots` 现在返回 `(Vec<SignalSnapshot>, SignalBuildStats)`：

- 统计 `regime_missing` 和 `rotation_missing`
- `compute_signals` 发现缺失时打印 warning：
  > "Data-starved signals detected: 3/15 signals used fallback defaults (regime_missing=2, rotation_missing=1)."

`SignalSummary` 新增字段：

- `data_starved_count: usize`
- `data_starved_warning: Option<String>`

**效果：**

- 之前：缺失 regime 静默使用 50.0（Watch），缺失 rotation 静默使用 40.0
- 现在：每次 `compute_signals` 都会统计并暴露 data-starved 比例

### 2.7 默认 `export-report` 增加 fail-loud 保护

**改造文件：** `crates/app-service/src/lib.rs`

默认 `export-report`（未传 `--date`）现在会先调用 `explain_latest_gate(scope)`：

- 如果 `latest_gate_advanced == Some(false)`，直接拒绝导出
- 错误信息会包含 latest-gate alerts
- 显式 `--date` 仍然保留，可用于导出历史日报

**效果：**

- 默认日报不会再静默导出旧的 dashboard 日期
- 如果上游 stage 没有推进，CLI 会先把问题暴露出来，而不是生成看似成功的旧报告

## 3. 当前系统与之前相比，用户最能直接感知到的变化

1. **GLOBAL dashboard 不再被跨市场休市卡住**
   - CN 开市+HK 休市时，dashboard 可以正常推进

## 3. P3 明确延迟：Evidence Score / Weight 不进入当前阶段

P3（Evidence 评分与权重）不是本轮目标，而是被明确推迟，直到满足以下三个门限：

1. **Evidence Assets > 1000**
2. **Historical Replay 稳定运行 > 30 天**
3. **Calibration Baseline 稳定 > 2 周期**

**原因：**

- V7 历史复盘已经发现 SRD-strong 的全历史表现接近随机，但存在明显 **Regime Dependency**（特定 regime 下正收益，其他 regime 下负收益）。
- 在没有足够资产分布前设计 Evidence 权重，容易把 regime-specific bias 伪装成普遍规律。
- 因此 V8 阶段只做「积累」，不做「赋权」。

# 阶段性更新（2026-07-13）：V7 Workflow 命令落地

## 1. 这轮工作的目标

在 V7 Research Platform 1.0（已冻结）之上，新增三个**工作流命令**，把 CLI 从“功能堆砌”转向“按研究场景组织”：

- `research observe`：把每日研究观察所需的多条原始命令（SRD / Stretch / Analytics / Health）聚合成一份日报。
- `research replay`：替代外部 PowerShell 脚本，把历史条件 × 周期的分析批量保存为 V8 Evidence Asset。
- `data-health`：把 `check-data-health` 与 `export-data-health-report` 两条原始命令合并为一次调用。

核心原则：工作流命令不修改 V7 平台语义，也不替换底层原始命令；它们只是对现有能力的 orchestration。

## 2. 已完成的阶段性成果

### 2.1 新增 `research observe` 工作流

- 聚合 `research-srd`、`research-stretch`、`research analytics`（默认条件 `srd-strong`、默认周期 `20`）和 `check-data-health`。可通过 `--condition` 与 `--horizon` 自定义。
- 输出到 `reports/research-observe-{scope}-{date}.md`。
- 实现位置：
  - `apps/cli/src/main.rs`：新增 `ResearchCommand::Observe`
  - `apps/cli/src/commands/research.rs`：新增 `handle_research_observe`
  - 复用已有的 `compute_srd_input`、`compute_stretch_input`、`compute_analytics_input` 和 `context.check_data_health()`。

### 2.2 新增 `research replay` 工作流

- 默认条件：`srd-strong`、`stretch-extreme-crowding-momentum`。
- 默认周期：20、60 交易日。
- 对每组条件 × 周期计算 Evidence，通过 `WorkspaceManager::write_evidence` 保存到 `workspace/evidence/replay/RA-XXXXXX/`。
- 输出与旧 PowerShell 脚本一致的索引文件到 `shadow-production/historical-replay/`：
  - `manifest.json`
  - `summary.json`
  - `evidence-index.json`
  - `candidate-index.json`
- 实现位置：
  - `crates/app-service/src/lib.rs`：新增 `ReplayEvidenceSummary` 与 `AppContext::research_replay`
  - `apps/cli/src/main.rs`：新增 `ResearchCommand::Replay`
  - `apps/cli/src/commands/research.rs`：新增 `handle_research_replay`

### 2.3 新增 `data-health` 工作流

- 一次调用同时运行数据健康检查并导出 Markdown 报告。
- 输出 JSON 包含 `check` 和 `export` 两部分摘要。
- 原始命令 `check-data-health` 与 `export-data-health-report` 仍然保留。
- 实现位置：
  - `apps/cli/src/main.rs`：新增 `Command::DataHealth`
  - `apps/cli/src/commands/diagnostics.rs`：新增 `handle_data_health`

### 2.4 文档更新

- `README.md`：在 V7 章节中增加 Workflow 命令说明。
- `docs/日常操作手册.md`：更新命令频率表和每日使用节奏，标注新命令与原始命令的对应关系。
- `docs/阶段性更新.md`：追加本章节。
