# V3 设计规划

## 1. 目标概述

V3 聚焦 CLI 体验升级与智能化分析能力，目标是在不改动桌面端 UI 的前提下，实现三件事：

1. **一键导出最新报告**：自动检测数据新鲜度，必要时自动刷新，最终导出报告。
2. **命令行进度输出**：在耗时较长的 CLI 命令执行过程中，向 stderr 输出进度信息。
3. **大模型分析解读**：将每日报告发送给配置好的大模型，获取分析解读与操作策略建议。

---

## 2. 功能设计

### 2.1 sync-and-export 一键导出

**问题背景**
当前 `export-report` 在 dashboard latest date 落后时会直接 fail-loud，用户需要手动执行 `refresh-all` 后再导出。V3 希望把这个过程自动化。

**命令设计**
```bash
cargo run -p quant-cli -- sync-and-export --scope global
cargo run -p quant-cli -- sync-and-export --scope cn --date 2026-05-08
cargo run -p quant-cli -- sync-and-export --to 2026-05-10 --run-backtests
```

**行为逻辑**
1. 如果显式传了 `--date`，跳过自动刷新，直接导出该日期报告（与现有 `export-report --date` 语义一致）。
2. 如果未传 `--date`：
   - 调用 `explain_latest_gate(scope)` 检查 gate 状态。
   - 若 gate 已推进到最新，直接导出。
   - 若 gate 落后，自动调用 `refresh_pipeline(to, scope, ...)` 进行刷新。
   - 刷新完成后**再次**检查 gate。
   - 若 gate 仍落后，fail-loud 报错退出。
   - 若 gate 推进成功，导出报告。
3. 返回 JSON 包含报告路径、刷新状态、gate 信息。

**约束**
- 不修改现有 `export-report` 行为。
- 不将业务逻辑放入 CLI match arms。
- `--run-backtests` 默认 `true`（与 `refresh-all` 一致）。

---

### 2.2 CLI 进度输出

**问题背景**
当前所有 CLI 命令只在执行完成后输出一次 JSON，用户在等待 `refresh-all` 或 `compute-macro` 等耗时命令时没有任何状态反馈。

**设计**
- 在 `refresh-all`、`sync-and-export` 以及所有 `compute-*` 命令执行期间，向 **stderr** 输出进度信息。
- 格式示例：
  ```
  [1/7] Starting ingest...
  [2/7] Computing indicators...
  ...
  [7/7] Running backtests...
  ```
- 进度百分比复用桌面端现有映射：ingest=20%, indicators=40%, macro=60%, rotation=75%, strategy=88%, signals=92%, backtests=96%。
- 增加 `--quiet` 参数用于脚本场景，完全抑制进度输出。
- **stdout JSON 输出不受影响**，保证下游管道和脚本解析兼容性。

### 2.3 大模型分析解读

**问题背景**
用户希望将系统生成的每日报告自动发送给大模型，由 AI 提供额外的分析视角和操作策略建议。

**命令设计**
```bash
# 配置大模型参数（持久化存储）
cargo run -p quant-cli -- set-llm-config \
  --base-url https://api.openai.com/v1 \
  --model gpt-4o \
  --timeout-secs 60

# 配置 API Key（安全存储）
cargo run -p quant-cli -- set-llm-api-key --key sk-xxxxxxxx

# 发送报告给大模型分析
cargo run -p quant-cli -- analyze-with-llm --scope global --date 2026-05-08
```

**技术方案**
- **API 客户端**：使用 `async-openai` crate（v0.34+），支持自定义 `base_url` 和 `api_key`，兼容 OpenAI 协议的标准接口。
- **配置存储**：
  - `base_url`、`model`、`timeout` 存入 SQLite `app_config` 表。
  - `api_key` 优先存入 OS keyring（Windows Credential Manager / macOS Keychain / Linux Secret Service），keyring 不可用时回退到 SQLite `credential_store` 表（明文，有警告提示）。
- **调用方式**：同步阻塞调用（非流式），等待完整响应后保存。
- **Prompt 设计**：System 消息设定角色为量化分析师；User 消息包含报告 Markdown + 请求分析解读和操作策略。
- **输出**：LLM 响应保存为 `reports/llm-analysis-{scope}-{date}.md`，并注册到 `report_snapshot` 表，可被桌面端 Recent Reports 识别。

**安全约束**
- API Key 绝不出现在 stdout、stderr、日志、错误信息、JSON 输出或测试快照中。
- 前端/桌面端不接触 API Key，仅在 Rust CLI / app-service 层处理。

## 3. 数据流与模块边界

```
CLI (apps/cli)
  ├── sync-and-export
  │     └── AppContext::sync_and_export()
  │           ├── explain_latest_gate() [检查]
  │           ├── refresh_pipeline()    [如需要]
  │           └── export_report_with_scope() [导出]
  ├── compute-* / refresh-all
  │     └── AppContext::*() + progress callback
  ├── set-llm-config / set-llm-api-key
  │     └── AppContext::set_llm_*()
  └── analyze-with-llm
        └── AppContext::analyze_report_with_llm()
              ├── get_llm_config() + get_llm_api_key()
              ├── export_report_with_scope() [获取报告]
              ├── async-openai Client [调用大模型]
              └── 保存 llm-analysis-*.md

app-service (编排层)
  ├── 新增 sync_and_export() 方法
  ├── 新增 progress callback 参数到 refresh_pipeline / compute_*
  └── 新增 llm 模块（config + client + prompt builder）

market-store (存储层)
  ├── 新增 app_config 读写 helper
  └── 新增 credential_store 读写 helper

core-domain (契约层)
  └── 新增 LlmConfig、LlmAnalysisResult 类型
```

---

## 4. 实现顺序

**第一阶段：基础铺垫（可并行）**
1. `market-store` 增加 SQLite `app_config` / `credential_store` 读写 helper。
2. `core-domain` 增加 `LlmConfig`、`LlmAnalysisResult` 类型。
3. Workspace 引入 `async-openai` + `keyring` 依赖。
4. 抽离桌面端进度映射为共享常量。
5. `app-service` 增加 progress callback 基础设施。

**第二阶段：核心功能（可并行）**
6. `sync-and-export` CLI 命令 + AppContext 方法。
7. CLI 进度输出（stderr）。
8. `app-service` LLM 客户端模块（config + API 调用）。
9. CLI LLM 命令（set-config / set-api-key / analyze-with-llm）。

**第三阶段：测试与验证**
10. Config 存储 round-trip 单元测试。
11. `sync-and-export` gate-after-refresh 逻辑单元测试。
12. LLM 客户端 mock server 单元测试。
13. 端到端手动 QA。

## 5. 风险与约束

| 风险 | 缓解措施 |
|------|---------|
| `app-service` 已经是 monolith（795+ 行），继续膨胀 | LLM 逻辑隔离为内部 `llm` 模块；若超过 ~200 行则拆分为独立 crate |
| keyring 在某些环境（WSL、headless Linux）不可用 | 自动探测 keyring 可用性，不可用时回退到 SQLite credential_store 并显式警告 |
| LLM API 调用超时或失败 | 可配置 timeout（默认 60s），报错时隐藏 API key |
| 报告内容超过 LLM context limit | V3 先发送完整报告；若后续遇到 limit，再考虑分段或摘要策略 |
| 现有 stdout JSON 契约被破坏 | 进度严格输出到 stderr，stdout 保持纯 JSON |

---

## 6. 验收标准

- [ ] `sync-and-export --scope global` 在数据最新时直接导出；在数据落后时自动刷新后导出；刷新失败时明确报错。
- [ ] `refresh-all` 执行期间 stderr 出现 `[x/y] Starting ...` 进度信息；加 `--quiet` 后 stderr 无进度。
- [ ] `set-llm-config` / `set-llm-api-key` 配置可持久化。
- [ ] `analyze-with-llm` 生成 `reports/llm-analysis-*.md` 文件。
- [ ] `cargo check --workspace` 和 `cargo test --workspace` 通过。
- [ ] 任何输出中都不包含 API Key。
